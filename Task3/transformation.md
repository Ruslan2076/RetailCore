# Трансформация RetailCore: точки трансформации и целевая архитектура первого этапа

Документ опирается на `requirements.md` (ФТ, НФТ, О, Г-01…Г-16), `architecture-canvas.md` (Г-17…Г-26, проблемные зоны [!1]–[!6]) и `as-is-context.md`. Новые пробелы продолжают нумерацию с Г-27. Диаграмма целевого состояния: `to-be-context.puml`, `to-be-context.svg`, `to-be-context.png`.

## 1. Бизнес-цель

Первый этап трансформации должен дать бизнесу три вещи, не рискуя оформлением, оплатой и обещанием по доставке:

- одну доверенную картину заказа для клиента, поддержки, логистики и функций бизнеса вместо нескольких расходящихся;
- меньше ручной работы и дублей на стыках с логистическими партнёрами;
- основу, к которой через год подключаются новые сервисы (персонализация, партнёрские сценарии) без изменений в ядре оформления.

Попутно первый этап снимает с операционной Oracle часть нагрузки и не добавляет в неё новой логики и новых потребителей, то есть готовит постепенный отказ от неё, но саму замену не начинает.

Каждый шаг должен объясняться через бизнес-проблему и давать эффект до завершения всей программы (О-11).

## 2. Уточнённые требования

| Исходная формулировка | Что показал анализ текущего состояния | Рабочая формулировка для первого этапа |
|---|---|---|
| Перейти к сервисной архитектуре, вынести ядро из монолита | Ядро оформления держит деньги, резервы и статусы в одной длинной транзакции; вынос тянет скрытые зависимости; вариант «переписать всё» бизнес не принимает | Путь записи заказа остаётся в монолите. Первым выносится путь чтения: события, состояние заказа, аналитика |
| Единый источник истины по состоянию заказа (НФТ-07) | Статусы пишут четыре механизма, есть специальные статусы партнёров; централизовать запись сейчас рискованно | Источником истины по записи остаются монолит и Oracle. Единой точкой чтения состояния и истории становится сервис состояния заказа |
| Понятный статус для клиента и детальный для оператора (ФТ-10, ФТ-11) | Формальный цикл статусов не совпадает с фактическим; клиенту нужна абстракция, оператору причина | Двухуровневая модель: клиентский статус и внутреннее состояние с причиной, собранные из фактических статусов через слой перевода |
| Прозрачность не должна ухудшиться на переходе (НФТ-05) | Поддержка боится потери видимости при переходе кусками | Новый путь чтения работает параллельно со старым, пока не подтверждено совпадение; переключение потребителя обратимо |
| Снизить зависимость оформления от синхронных вызовов (НФТ-02) | Цепочка синхронных вызовов в одном методе, резерв доставки без компенсации при сбое оплаты, нет ключа идемпотентности | На первом этапе цепочку не перестраиваем. Добавляем защиту от повторного оформления и компенсацию резерва доставки |
| Согласованные цифры для маркетинга, финансов и операций (ФТ-17) | Причина расхождений в разных витринах и разной трактовке отмен, возвратов и промо, а не только в источнике | Аналитика строится на каноническом наборе событий с согласованными определениями показателей |
| Быстрее запускать новые типы акций (НФТ-08) | Три механизма расчёта стоимости; резервный расчёт скидки по урезанным правилам; новые правила добавляются в любой из слоёв | Новые механики промо реализуются только в промо-сервисе за единым контрактом; старый PL/SQL-расчёт замораживается и сверяется с новым |
| Подготовка к отказу от Oracle (НФТ-16) | Логика в PL/SQL и интеграция через таблицы делают замену отдельным крупным проектом | Первый этап не добавляет логики и потребителей в Oracle и снимает с неё аналитическую нагрузку и обмен через staging-таблицы |

## 3. Ограничения

| ID | Ограничение | Как учтено в целевом состоянии |
|---|---|---|
| О-01, О-02 | Бизнес нельзя останавливать; изменения поэтапные, с откатом в зонах высокого риска | Изменения в зоне оформления минимальны и закрыты переключателями; остальные изменения на пути чтения |
| О-03, О-04 | Потребители не перейдут на новые правила одновременно; наследие нельзя убрать за шаг | Старые пути чтения и обмена работают параллельно с новыми, пока потребители переходят по одному |
| О-05, О-07 | Отказ от Oracle не ценой остановки; в Oracle лежат логика и интеграции | Oracle остаётся операционной БД; меняется только то, кто и как из неё читает |
| О-06 | Собственный ДЦ, ресурсы близки к пределу, расширение через закупки | Новые компоненты требуют мощностей; объём нужно оценить до старта (Г-29). Вынос аналитики частично освобождает ресурсы Oracle |
| О-09 | Интерфейсы и SLA партнёров вне контроля | Внешние модели изолируются слоем перевода; изменений на стороне партнёров не требуется |
| О-11 | Каждый этап даёт бизнес-эффект | У каждой точки трансформации есть бизнес-эффект и метрика (раздел 10) |
| О-12 | Нельзя добавлять слой сложной оркестрации | Новые части не оркестрируют заказ, а потребляют события и отвечают на чтение; слои перевода не принимают бизнес-решений |

## 4. Препятствия текущего состояния

| Препятствие | Зона AS-IS | Как мешает цели |
|---|---|---|
| Статусы меняют сервис заказов, платёжный модуль, пакетные процедуры и админка; три статуса вне формального цикла; специальные статусы партнёров | [!2] | Нет одной картины заказа; поддержка ходит по системам, клиент видит противоречия |
| Нет потока бизнес-событий; историю заказа восстанавливают вручную; корреляционные идентификаторы не везде | [!5], [!6] | Нельзя объяснить, что произошло с заказом; аналитика догоняет реальность |
| Аналитика и BI читают операционную Oracle напрямую, в том числе в пиковые окна; несколько «почти канонических» моделей заказа | [!3], [!5] | Нагрузка на оформление в пики; разные цифры у функций |
| Логистические интеграции разнородны: REST, брокер, выгрузки, .NET через staging-таблицы; разная семантика доставки; дубли при повторах | [!4] | Ручные разборы, изменение обещанного срока, дубли заявок у партнёров |
| Экспорт для .NET-сервиса пишется до выбора маршрута и оплаты | [!3], [!4] | Партнёрский контур получает заказы, которые не будут подтверждены |
| Скидка считается тремя путями; резервный расчёт по урезанным правилам и без состава корзины | [!1], [!3] | Сумма зависит от пути расчёта; новые акции требуют изменений в нескольких слоях |
| Нет ключа идемпотентности на входе оформления; нет компенсации резерва доставки при сбое оплаты | [!1] | Дубли заказов и висящие резервы у партнёров |
| Правила маршрутов в четырёх слоях, ручные правки без журнала изменений | [!4] | Непредсказуемые побочные эффекты, поломки соседних сценариев |

## 5. Точки трансформации

### 5.1. Паспорта точек трансформации

К полям паспорта из шаблона добавлены «Почему подходит» и «Зависимости».

#### ТТ-1. Журнал бизнес-событий заказа и доставки

| Поле | Содержание |
|---|---|
| Проблема AS-IS | Нет потока событий; изменения заказа видны только как строки в таблицах Oracle, записанные четырьмя механизмами; корреляции по заказу нет |
| Бизнес-влияние | Единая картина заказа (Ц2), основа для новых сервисов (Ц5); без журнала невозможны ТТ-2, ТТ-3 и перевод .NET-сервиса на события |
| Почему подходит | Журнал не меняет поведение оформления: он наблюдает изменения, а не участвует в них. Отключение журнала не ломает заказ |
| Изменение | Ввести канонический набор событий заказа и доставки (создан, ожидает ручной проверки, ожидает доставки, ожидает оплаты, подтверждён, оплачен, отгружен, доставлен, частично отменён, отменён, срок доставки изменён, возврат) с `event_id`, `order_id`, `correlation_id`, временем и источником изменения. События формируются из фактических изменений заказа и публикуются в брокер |
| Способ захвата изменений | Открытое решение. Публикация из Java-кода (outbox) не видит изменений из пакетных процедур и админки, поэтому предпочтителен захват на уровне данных: из журнала изменений БД или из таблицы истории статусов, если в неё пишут все четыре механизма (Г-28). Выбор после аудита писателей (Г-10, Г-23) |
| Что не делаем | Не меняем логику переходов статусов и места их записи; не переносим события в роль команд, по которым монолит что-то делает |
| Зависимости | Схема таблиц заказа и истории статусов; перечень писателей статусов; брокер (продукт и мощность не определены, Г-30) |
| Метрика проверки | Доля изменений заказа, попавших в журнал (сверка с Oracle); задержка от изменения до события |
| Риски | Захват пропускает изменения из пакетных процедур; события технические, а не бизнесовые, если перевод сделан плохо; дополнительная нагрузка на Oracle от захвата |
| Следующий шаг | Аудит писателей статусов и таблицы истории; согласовать перечень событий с поддержкой, логистикой и аналитикой |

#### ТТ-2. Сервис состояния заказа и двухуровневая модель статусов

| Поле | Содержание |
|---|---|
| Проблема AS-IS | Карточка заказа не единый источник; клиент, письмо, оператор, склад и логистика видят разные статусы; формальный цикл не совпадает с фактическим |
| Бизнес-влияние | Меньше обращений «что с заказом» и внутренних эскалаций (Ц2, Ц4); поддержка отвечает без хождения по системам |
| Почему подходит | Функция только читает. Если новый путь ошибается, потребителя возвращают на старое чтение переключателем. Это безопасная первая функция для постепенного вытеснения |
| Изменение | Сервис состояния строит модель чтения из журнала событий: клиентский статус, внутреннее состояние с шагом и причиной отклонения, признак ручного сценария, история изменений срока, состава, способа доставки и статуса. Слой перевода статусов переводит фактические статусы монолита и специальные статусы партнёров в новую модель. Личный кабинет и инструменты поддержки читают состояние из сервиса |
| Что не делаем | Не переносим запись статусов; ручные действия поддержки (перевод в технический статус, флаги) по-прежнему выполняются через админку монолита |
| Зависимости | ТТ-1; фактическая модель статусов и специальные статусы партнёров (Г-11, Г-25); требования к допустимой задержке (Г-06) |
| Метрика проверки | Доля совпадений состояния в сервисе и в Oracle; доля обращений «что с заказом»; время обработки обращения; число внутренних эскалаций |
| Риски | Задержка модели чтения создаёт новое расхождение; неверный перевод статусов; перевод специальных статусов ломает сценарии маркетплейсов |
| Следующий шаг | Восстановить фактическую модель статусов по журналу переходов; согласовать клиентские статусы и причины с поддержкой |

#### ТТ-3. Аналитический контур на событиях

| Поле | Содержание |
|---|---|
| Проблема AS-IS | Аналитика и BI читают операционную Oracle, тяжёлые выборки в пиковые окна; несколько моделей заказа; поле скидки берётся из разных мест |
| Бизнес-влияние | Одна цифра по выручке кампании для маркетинга, финансов и операций (Ц2); меньше нагрузки на оформление в пики (Ц1) |
| Почему подходит | Аналитика не участвует в оформлении; отчёты можно строить параллельно на старом и новом источнике и сверять |
| Изменение | Отдельное аналитическое хранилище, наполняемое из журнала событий; согласованные определения отмены, возврата, промо и выручки; перевод на новое хранилище в первую очередь самых тяжёлых выгрузок |
| Что не делаем | Не переписываем все отчёты; лёгкие выборки из Oracle временно остаются; не меняем BI-инструменты |
| Зависимости | ТТ-1; реестр аналитических потребителей Oracle (Г-10); согласие маркетинга, финансов и операций на определения |
| Метрика проверки | Доля тяжёлых аналитических запросов к операционной Oracle; время ответа оформления в окна выгрузок; число расхождений одного показателя между витринами |
| Риски | Новые цифры не совпадут со старыми, и функции не примут новый источник; ретроактивные корректировки в batch не попадут в события |
| Следующий шаг | Выбрать две-три самые тяжёлые выгрузки и один спорный показатель выручки для параллельной сверки |

#### ТТ-4. Единый контракт статуса доставки и слой логистических интеграций

| Поле | Содержание |
|---|---|
| Проблема AS-IS | Каждая логистическая интеграция устроена по-своему; разная семантика доставки и дедупликация; дубли заявок при повторах; .NET-сервис читает staging-таблицу, в которую пишется ещё не подтверждённый заказ; настройки приоритетов правят вручную без журнала |
| Бизнес-влияние | Меньше ручных разборов в логистике и дублей у партнёров (Ц4); меньше претензий к изменению срока доставки (Ц1) |
| Почему подходит | Интеграции находятся за оформлением и не блокируют его, кроме синхронного резерва слота, который на первом этапе не трогаем. Партнёров можно переводить по одному |
| Изменение | Слой логистических интеграций переводит статусы и форматы каждого партнёра в единый контракт статуса доставки и публикует события доставки в журнал; обработка входящих подтверждений идемпотентна по ключу заявки; .NET-сервис получает заказы из события «подтверждён» вместо чтения INT_ORDER_EXPORT; изменения настроек приоритетов фиксируются с автором и временем |
| Что не делаем | Не выносим логику выбора маршрута из монолита; не меняем синхронный резерв слота при оформлении; не переписываем .NET-сервис |
| Зависимости | ТТ-1; реестр партнёров и способов интеграции (Г-22); владелец .NET-сервиса; нужны ли .NET-сценариям заказы до подтверждения (Г-31) |
| Метрика проверки | Доля дублей заявок у партнёров; число ручных разборов в логистике; время от заявки до подтверждения партнёром; доля заказов с изменённым сроком доставки |
| Риски | Слой перевода обрастает бизнес-логикой и становится новым монолитом интеграций; недооценка исключений (частичная поставка, крупногабарит, ручная переадресация); .NET-сценарии ломаются при смене момента экспорта |
| Следующий шаг | Составить реестр партнёров; выбрать одного партнёра с асинхронными подтверждениями для первого перевода |

#### ТТ-5. Изоляция расчёта скидки за контрактом промо-сервиса

| Поле | Содержание |
|---|---|
| Проблема AS-IS | Три пути расчёта скидки; резервный PL/SQL-расчёт по урезанным правилам и без состава корзины включается при любом пустом ответе промо-сервиса; новые правила добавляются в разные слои |
| Бизнес-влияние | Быстрее запуск типовых акций (Ц3); одна сумма заказа независимо от пути расчёта |
| Почему подходит | Промо-сервис уже существует и вызывается через отдельный интерфейс; изменение затрагивает одну точку вызова в монолите |
| Изменение | В монолите промо вызывается через адаптер с явным результатом: скидка есть, скидки нет, сервис недоступен. Резервный расчёт включается только при недоступности. Каждый случай резервного расчёта фиксируется, а для части заказов параллельно считается основным путём и сверяется. Новые механики акций реализуются только в промо-сервисе; `legacy_promo_pkg` замораживается |
| Что не делаем | Не трогаем базовый расчёт цены, сервисный сбор маркетплейса и региональные надбавки; не удаляем резервный путь |
| Зависимости | Смысл пустого ответа промо-сервиса (Г-19); принадлежность промо-сервиса (Г-24); маркетинг как владелец правил; релиз монолита |
| Метрика проверки | Доля заказов с резервным расчётом; расхождение скидки между путями; время от решения о новой акции до запуска |
| Риски | Изменение трактовки пустого ответа меняет суммы уже действующих акций; это денежный путь оформления |
| Следующий шаг | Выяснить поведение промо-сервиса при ошибке; включить журналирование пути расчёта без изменения логики |

#### ТТ-6. Защитные изменения оформления без переноса логики

| Поле | Содержание |
|---|---|
| Проблема AS-IS | Повторный вызов оформления создаёт новый заказ, строку экспорта и резерв доставки; при сбое платёжной сессии резерв доставки остаётся без компенсации |
| Бизнес-влияние | Меньше дублей заказов, висящих резервов и связанных с ними обращений (Ц1, Ц4) |
| Почему подходит | Изменения точечные, закрываются переключателем и не меняют порядок шагов оформления |
| Изменение | Ключ идемпотентности на входе оформления; при неуспехе платёжной сессии резерв доставки снимается или помечается для отмены; корреляционный идентификатор передаётся во все вызовы оформления |
| Что не делаем | Не перестраиваем синхронную цепочку, не выносим оркестрацию оплаты, не меняем транзакцию оформления |
| Зависимости | Границы транзакции оформления (Г-17); поддерживают ли партнёры отмену резерва (Г-27); покрытие тестами (Г-26); защита от повторов выше по цепочке вызова |
| Метрика проверки | Доля дублей заказов; число заказов в ожидании оплаты с активным резервом доставки |
| Риски | Зона высокого риска: ошибка бьёт по конверсии; без тестов регрессию не поймать до продуктива |
| Следующий шаг | Получить ответы по Г-17, Г-26, Г-27; до них ТТ-6 не стартует |

## 7. Приоритизация

Критерии: бизнес-эффект, реализуемость, проверяемость, риск текущего состояния, риск зависимости, обратимость.

| Порядок | Изменение | Обоснование |
|---|---|---|
| 0 | Подготовка: базовая линия метрик, аудит писателей статусов и потребителей Oracle, фактическая модель статусов по журналу переходов | Без базовой линии эффект этапа не доказать (О-11); без аудита нельзя выбрать способ захвата изменений |
| 1 | ТТ-1 Журнал событий | Основа для ТТ-2, ТТ-3, ТТ-4 и новых сервисов; не меняет поведение оформления; легко отключается |
| 2 | ТТ-2 Сервис состояния | Прямой эффект для поддержки и клиента; только чтение; переключение обратимо |
| 3 | ТТ-3 Аналитика на событиях | Снимает нагрузку с Oracle и решает спор о цифрах; проверяется параллельной сверкой отчётов |
| 4 | ТТ-4 Контракт статуса доставки | Эффект по ручным разборам и дублям; затрагивает внешних партнёров, поэтому идёт по одному партнёру и после ТТ-1 |
| 5 | ТТ-5 Изоляция промо | Эффект по скорости акций; денежный путь, поэтому начинается с журналирования и сверки без изменения логики |
| 6 | ТТ-6 Защитные изменения оформления | Эффект по дублям и висящим резервам; зона высокого риска, стартует только после ответов по Г-17, Г-26, Г-27 |

ТТ-3 и ТТ-4 можно вести параллельно после ТТ-1. ТТ-5 не зависит от ТТ-1 и может идти параллельно с ТТ-2, если есть команда: его первый шаг только наблюдает.

## 8. Целевая архитектура первого этапа

![TO-BE контекст RetailCore](to-be-context.png)

Верхняя половина диаграммы показывает путь записи заказа: монолит и Oracle, где на первом этапе меняются только адаптер промо и точка входа оформления. Нижняя половина показывает новый путь событий и чтения, который выносится первым.

### 8.1. Карточка целевой архитектуры

| Раздел | Содержание |
|---|---|
| Цель первого этапа | Проверить, что единая картина заказа, собранная из событий, снижает обращения, ручные разборы и расхождения цифр без изменения пути записи заказа |
| Границы | Журнал событий охватывает все заказы и каналы. Потребители переключаются постепенно: сначала инструменты поддержки, затем личный кабинет для части клиентов, затем аналитика по одной выгрузке. Логистика переводится по одному партнёру. Промо и защитные изменения оформления включаются переключателями на часть трафика |
| Основной сценарий | Клиент оформляет заказ как сейчас. Изменения заказа попадают в журнал событий. Сервис состояния обновляет клиентский статус и внутреннее состояние. Клиент в личном кабинете и оператор поддержки видят состояние из сервиса. Логистический слой публикует события доставки. Аналитика и новые потребители читают события, а не Oracle |
| Исключения | Ручная проверка, ожидание доставки, ожидание оплаты, частичная отмена, изменение срока доставки, ручной перевод статуса поддержкой, специальные статусы маркетплейсов и логистического партнёра: всё отражается событием и внутренним состоянием с причиной |
| Компоненты | Монолит и Oracle без изменения пути записи; новые: захват изменений и публикация событий, брокер с каноническим контрактом событий, сервис состояния заказа со слоем перевода статусов, аналитическое хранилище; изменяемые: слой логистических интеграций, вход .NET-сервиса, адаптер промо и точка входа оформления в монолите |
| Данные и состояния | `order_id`, `event_id`, `correlation_id`; клиентский статус; внутреннее состояние с шагом и причиной; история изменений срока, состава, доставки, статуса; единый статус доставки |
| Интеграции | Захват изменений из Oracle, публикация в брокер; сервис состояния и аналитика потребляют события; каналы и поддержка читают сервис состояния по API; логистический слой переводит форматы партнёров; .NET-сервис потребляет событие подтверждения |
| Метрики | Раздел 10 |
| Ограничения | Раздел 3 |

### 8.2. Что остаётся, что изолируется, что выносится первым

| Часть | Решение на первом этапе | Почему |
|---|---|---|
| Оформление заказа (создание, расчёт суммы, резерв товаров, выбор маршрута, резерв доставки, платёжная сессия) | Остаётся в монолите; только защитные изменения ТТ-6 за переключателем | Денежный и конверсионный путь; вынос тянет скрытые зависимости |
| Оркестрация оплаты | Остаётся в монолите без изменений | Платёжный путь; жёсткая зависимость от провайдера |
| Маршрутизация доставки | Остаётся в монолите без изменений | Правила в четырёх слоях, сначала стабилизация интеграций |
| Запись статусов (все четыре механизма) | Остаётся без изменений | Сначала модель чтения и фактическая модель статусов |
| PL/SQL-логика в Oracle | Остаётся; `legacy_promo_pkg` замораживается | Перенос логики из БД не входит в первый этап; новых правил в БД не добавляем |
| Расчёт скидки | Изолируется за адаптером с явным результатом (ТТ-5) | Денежный путь, но одна точка вызова; новые механики уходят в промо-сервис |
| Логистические партнёры | Изолируются слоем перевода с единым контрактом статуса доставки (ТТ-4) | Чужие модели не должны проникать в новую модель статусов |
| Статусы монолита и партнёров | Изолируются слоем перевода в сервисе состояния (ТТ-2) | Фактические и специальные статусы не должны становиться клиентскими |
| Журнал событий | Выносится первым (ТТ-1) | Только наблюдает, не участвует в оформлении |
| Чтение состояния и истории заказа | Выносится первым (ТТ-2) | Только чтение, обратимое переключение |
| Аналитическое чтение | Выносится в отдельное хранилище (ТТ-3) | Снимает нагрузку с операционной БД, проверяется параллельной сверкой |
| Административные действия поддержки | Остаются в админке монолита; чтение состояния переходит в сервис состояния | Ручные механизмы нужны, пока нет автоматической маршрутизации исключений |

### 8.3. Границы

- Граница записи. Всё, что создаёт заказ, меняет деньги, резервы и статусы, остаётся в монолите и Oracle. Новые части ничего не пишут в Oracle.
- Граница чтения. Состояние и история заказа для личного кабинета, поддержки, аналитики и новых сервисов читаются из сервиса состояния и аналитического хранилища, а не из Oracle.
- Граница событий. Канонический набор событий заказа и доставки — единственный контракт между монолитом и новыми частями. Его владелец должен быть назначен до запуска ТТ-1 (Г-32).
- Граница внешних моделей. Статусы маркетплейсов и логистических партнёров переводятся в каноническую модель в слоях перевода и дальше не распространяются.

### 8.4. Границы согласованности

| Граница | Операция | Сейчас | На первом этапе |
|---|---|---|---|
| Оформление заказа | Запись заказа, резерв, служебные записи, статус | Одна длинная транзакция в монолите | Без изменений; добавляются ключ идемпотентности и компенсация резерва доставки (ТТ-6) |
| Фиксация изменения заказа | Изменение статуса или атрибутов любым из четырёх механизмов | Запись в Oracle | Без изменений; событие формируется из зафиксированного изменения, доставка не реже одного раза, потребители отбрасывают повторы по `event_id` |
| Состояние заказа для чтения | Клиентский статус, внутреннее состояние, история | Читается из Oracle разными интерфейсами | Модель чтения обновляется из событий с задержкой; допустимая задержка не определена (Г-06), интерфейс показывает время последнего обновления |
| Подтверждение доставки партнёром | Приём подтверждения и обновление статуса доставки | Разные механизмы, дедупликация по-разному | Через слой логистических интеграций, идемпотентно по ключу заявки |
| Аналитика | Витрины и отчёты | Прямое чтение Oracle, пакетно и почти в реальном времени | Наполнение хранилища из событий; ретроактивные корректировки тоже идут событиями |

### 8.5. Почему риск допустим

- Первые три точки трансформации лежат на пути чтения: они не меняют ни одной записи в Oracle и ни одного шага оформления.
- Каждое переключение потребителя обратимо: личный кабинет, поддержка и отчёты можно вернуть на старое чтение, пока старый путь не выключен.
- Новый путь чтения проверяется параллельно со старым: доля совпадений состояния и показателей измеряется до переключения.
- Изменения во внешних интеграциях идут по одному партнёру.
- Изменения в денежном пути (ТТ-5, ТТ-6) начинаются с наблюдения, закрыты переключателями и стартуют после ответов на открытые вопросы.

### 8.6. Что на первом этапе трогать опасно

| Участок | Почему опасно |
|---|---|
| Создание заказа и транзакция оформления | Деньги, резервы и статусы в одной транзакции; скрытые зависимости; нет данных о тестах |
| Оркестрация оплаты | Сбой напрямую останавливает оплату |
| Запись статусов и пакетные процедуры | Четыре писателя и специальные статусы партнёров; неизвестен полный перечень процедур (Г-23) |
| PL/SQL-пакеты и схема Oracle | Реестра потребителей нет (Г-10); изменения проявляются не там, где сделаны |
| Логика выбора маршрута | Правила в четырёх слоях, ручные исключения операционного блока |
| Старые API маркетплейсов | Специальные статусы и ветки расчёта; изменения требуют согласования с внешними площадками |

## 9. Разрыв

| Область | AS-IS | TO-BE первого этапа | Что нужно сделать |
|---|---|---|---|
| Процессы | Поддержка собирает картину заказа по нескольким системам; ручные правки маршрутов без журнала | Поддержка работает с одним экраном состояния; изменения настроек фиксируются | Перестроить рабочий экран поддержки; ввести журнал изменений настроек |

## 10. Метрики

Базовых значений нет (Г-08), поэтому этап 0 начинается со сбора базовой линии. Целевые значения согласуются со спонсором после её сбора.

| ТТ | Метрика | Как измерять |
|---|---|---|
| ТТ-1 | Доля изменений заказа, попавших в журнал; задержка от изменения до события | Сверка журнала с таблицей истории статусов Oracle |
| ТТ-2 | Доля совпадений состояния в сервисе и в Oracle; обращения «что с заказом»; время обработки обращения; внутренние эскалации | Сверка; разметка обращений в CRM поддержки |
| ТТ-3 | Доля тяжёлых запросов аналитики к операционной Oracle; время ответа оформления в окна выгрузок; расхождения показателя выручки между витринами | Мониторинг Oracle; метрики оформления; сверка отчётов |
| ТТ-4 | Доля дублей заявок у партнёров; число ручных разборов в логистике; время до подтверждения партнёром; доля заказов с изменённым сроком доставки | События доставки; журнал ручных разборов |
| ТТ-5 | Доля заказов с резервным расчётом; расхождение скидки между путями; время запуска новой акции | Журнал пути расчёта; сверка; учёт задач маркетинга |
| ТТ-6 | Доля дублей заказов; заказы в ожидании оплаты с активным резервом доставки | События журнала; сверка с резервами партнёров |
