# Анализ артефактов, по которым восстановлено текущее состояние

## 1. Использованные артефакты

| Артефакт | Что дал | Ограничения |
|---|---|---|
| Описание кейса RetailCore | Цели, стек, структура команд, инфраструктура, объём данных, основные зоны сложности | Нет количественных показателей; проблемы описаны на уровне областей |
| Исходная диаграмма AS-IS | Основные компоненты монолита, внешние системы, базовые связи с Oracle | Неполная (об этом сказано в самом кейсе); расхождения в разделе 3 |
| Интервью с техлидом монолита (Андрей) | Зона ответственности монолита, где живут правила, фактический жизненный цикл статусов, синхронные зависимости, длинные транзакции, наблюдаемость, кандидаты на вынос | Одна точка зрения; нет данных о тестах и релизах; «половина логики в БД» — оценка, а не замер |
| Интервью с разработчиком логистики и внешних интеграций (Ирина) | Способы интеграции с партнёрами, распределение правил маршрута по слоям, семантика доставки сообщений, дубли, ручные правки настроек | Нет перечня партнёров, объёмов и частоты сбоев |
| Интервью с разработчиком аналитики (Максим) | Источники данных аналитики, несколько моделей заказа, причины расхождения цифр, нагрузка на Oracle, состояние lineage | Нет перечня отчётов, витрин и окон выгрузки |
| Фрагмент кода `OrderProcessingService.createOrder` | Фактическая последовательность оформления, таблицы Oracle, статусы, обработка сбоев внешних вызовов | Один метод; комментарий в файле прямо говорит, что фрагмент намеренно показывает смешение ответственности, то есть он иллюстративный. Не видны транзакции, вызывающий код, реализации промо-сервиса и шлюзов, конфигурация, тесты |
| Интервью со спонсором и руководителем поддержки | Бизнес-цели, клиентские симптомы, ручные сценарии поддержки | Показывают симптомы, а не технические причины |

Логов, метрик, инцидентов, схемы БД и журналов событий среди артефактов нет. Поэтому узкие места подтверждены только качественно.

## 2. Что подтверждается несколькими артефактами

| Утверждение | Чем подтверждается |
|---|---|
| Часть бизнес-логики живёт в Oracle | Кейс; техлид (процедуры и пакеты); логистика (региональные исключения в таблицах, ночные SQL-скрипты); код (вызов `legacy_promo_pkg.calculate_discount`) |
| Интеграция через таблицы Oracle | Кейс (staging/shared tables); техлид (.NET-сервис через таблицы); логистика (staging-обмен, опрос таблиц); код (`INT_ORDER_EXPORT`, `RETRY_DELIVERY_QUEUE`) |
| Оформление — синхронная цепочка внешних вызовов | Кейс (синхронные вызовы платёжных провайдеров и доставки); техлид (платежи, скидки, наличие, иногда логистика); код (промо, доставка и оплата в одном методе) |
| Статусы меняются в нескольких местах и расходятся с формальным циклом | Кейс; техлид (четыре механизма переходов, специальные статусы партнёров); поддержка (разные статусы в разных интерфейсах); аналитика (рассинхрон статусов); код (статусы вне цикла, три способа записи состояния) |
| Правила разбросаны по технологическим слоям | Техлид (код, таблицы, конфигурация, административные таблицы); логистика (правила маршрута в четырёх слоях); код (надбавки в коде, правила маршрута в таблицах, скидка в PL/SQL) |
| Настройки правят вручную, иногда ночью | Спонсор (ночные изменения конфигов, договорённости с конкретными людьми); логистика (правка таблиц приоритетов и коэффициентов без полноценного change process) |
| Обещанный срок доставки меняется после оформления | Поддержка (частый повод обращений); логистика (подтверждение партнёра приходит позже, чем клиент увидел срок); код (отложенный резерв доставки с повтором через 10 минут) |
| Повторы создают дубли | Поддержка (платёжная сессия создаётся не с первого раза); логистика (дубли заявок у партнёров); аналитика (дубликаты в данных); код (нет ключа идемпотентности на входе) |
| Причина разных цифр у маркетинга, финансов и операций | Спонсор (симптом); аналитика (разные витрины, разная трактовка отмен, возвратов и промо, поле скидки из разных источников) |
| Аналитика нагружает операционную БД | Кейс (прямые выборки, долгие отчёты); аналитика (окна выгрузок уже ограничивали из-за нагрузки) |
| Сквозную историю заказа восстановить трудно | Поддержка (приходится ходить по нескольким системам); техлид (корреляционные идентификаторы есть не везде); логистика (расхождения между кодом, таблицами, логами и знаниями людей); аналитика (происхождение полей местами известно только авторам) |
| Единый набор событий заказа — возможный ранний шаг | Спонсор (единый слой событий заказа как пример этапа); логистика (унифицировать события, единый контракт статуса доставки); аналитика (канонический слой событий заказа и доставки); техлид (отделение чтения статусов) |

## 3. Расхождения между артефактами

| Расхождение | Что из этого следует |
|---|---|
| На исходной диаграмме AS-IS нет промо-сервиса, сервиса наличия, складов, CRM поддержки, пакетных переходов статусов, ночных SQL-скриптов и уведомлений клиенту. Расчёт цены показан одним компонентом, хотя механизмов три. Логистика показана через синхронный вызов и .NET-сервис, а способов интеграции с партнёрами четыре | В новой диаграмме эти элементы добавлены; исходную диаграмму нельзя использовать как эталон |
| Техлид называет формальный цикл `new → confirmed → reserved → paid → shipped → delivered / cancelled`. В коде есть `WAITING_MANUAL_REVIEW`, `DELIVERY_PENDING`, `PAYMENT_PENDING`; `CONFIRMED` ставится после создания платёжной сессии, до оплаты; доставка резервируется до подтверждения | Формальный цикл не годится как основа модели статусов. Фактическую модель нужно восстанавливать по журналу переходов (Г-11) |
| По словам техлида, резервный расчёт промо включается при недоступности промо-сервиса. В коде он включается при пустом ответе, а исключение сервиса на этом уровне не перехватывается | Неясно, что означает пустой ответ и что происходит при ошибке сервиса (Г-19) |
| Техлид называет синхронный вызов сервиса наличия и резерв товаров частью транзакции оформления. В методе оформления таких вызовов нет | Либо они выполняются до или после метода, либо фрагмент неполный (Г-21) |
| Техлид говорит, что при недоступности логистики заказ можно принять. Код это подтверждает, но в этой ветке платёжная сессия не создаётся | Путь оплаты для таких заказов не известен (Г-18) |
| По словам логистики, региональные исключения лежат в таблицах Oracle. В коде региональная надбавка зашита константой | Региональные правила живут минимум в двух местах |
| Спонсор и техлид относят пост-обработку заказа к кандидатам на ранние изменения. Поддержка называет её отклонения самыми болезненными для клиентов, а логистика главным риском трансформации называет недооценку исключений (частичная поставка, split shipment, ручная переадресация) | Противоречие ПР-2 из `interview-analysis.md` усилилось: пост-обработку нельзя считать безопасной зоной, пока её исключения не разобраны |

## 4. Ограничения анализа

- Ни один артефакт не даёт количественных данных. Нагрузка, время ответа, доля исключений и частота дублей оценены только качественно.
- Фрагмент кода подтверждает или опровергает конкретные утверждения интервью, но обобщать по нему всю систему нельзя.
- От каждой команды разработки опрошен один человек. Взгляды эксплуатации, платёжной команды и владельца .NET-сервиса не представлены.
