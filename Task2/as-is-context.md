# AS-IS: контекст и текущее устройство RetailCore

Диаграмма показывает систему такой, какая она есть сейчас, а не такой, какой её хотят видеть. Номера проблемных зон [!1]–[!6] совпадают с блоком 9 в `architecture-canvas.md`, пробелы Г-xx — с `requirements.md` и `architecture-canvas.md`.

Файлы диаграммы: `as-is-context.puml` (исходник), `as-is-context.svg`, `as-is-context.png`.

![AS-IS контекст RetailCore](as-is-context.png)

## 1. Что показано

- Внешние участники: клиенты, маркетплейсы, платёжные провайдеры, службы доставки и логистические партнёры, склады, BI; роли поддержки, операционного блока, маркетинга, финансов и операций.
- Части системы внутри границы RetailCore: каналы, Java-монолит с семью областями ответственности, сервисы вокруг ядра, логистический интеграционный контур с .NET-сервисом, асинхронный и пакетный контур, Oracle, административные инструменты, CRM поддержки, аналитические задания.
- Жирные красные стрелки: синхронная цепочка оформления заказа. Красные стрелки: проблемные связи (ручной перевод статуса, аналитическая нагрузка на Oracle). Пунктир: асинхронный, пакетный или табличный обмен.
- На стрелках указан состав данных с исходными именами полей и таблиц.

## 2. Ключевые интеграции и зависимости

Тип зависимости показывает, что происходит со сценарием при отказе или задержке: жёсткая блокирует сценарий, мягкая допускает задержку или повтор.

| № | Взаимодействие | Поток данных | Способ | Тип зависимости |
|---|---|---|---|---|
| 1 | Каналы → оформление заказа | `customerId, regionCode, channel, items, promocode, deliveryType, paymentType` | Синхронный вызов | Жёсткая |
| 2 | Маркетплейсы → оформление заказа | Заказы, обновления, статусы, включая специальные | Старые API маркетплейсов, механизм не описан | Жёсткая для заказов маркетплейсов |
| 3 | Расчёт цены → промо-сервис | `calculateDiscount(customerId, items, promocode)` | Синхронный вызов | Мягкая только при пустом ответе: тогда включается резервный расчёт. Что происходит при ошибке сервиса, не известно (Г-19) |
| 4 | Расчёт цены → Oracle | `legacy_promo_pkg.calculate_discount(customerId, regionCode, promocode)` | Синхронный SQL-вызов PL/SQL-пакета | Жёсткая в резервной ветке; состав корзины в расчёт не передаётся |
| 5 | Оформление → сервис наличия | Наличие товаров | Синхронный вызов | Жёсткая: задержка наличия тормозит оформление; место в цепочке не описано (Г-21) |
| 6 | Оформление → Oracle, ORDERS | Заказ, `totalAmount`, статус | Запись в общую БД в транзакции оформления | Жёсткая |
| 7 | Оформление → Oracle, INT_ORDER_EXPORT | `order_id, export_state = 'NEW', created_at` | Запись в staging-таблицу | Мягкая для оформления, жёсткая для партнёрских сценариев .NET |
| 8 | Oracle → .NET-сервис | Строки INT_ORDER_EXPORT | Чтение таблицы | Жёсткая для партнёрской логистики через .NET |
| 9 | Маршрутизация → Oracle | Правило по `regionCode, deliveryType, channel` | Чтение таблиц; при отсутствии правила берётся правило по умолчанию | Жёсткая |
| 10 | Оформление → служба доставки | `reserveSlot(order_id, regionCode, deliveryType, partnerCode)` | Синхронный вызов | Мягкая для приёма заказа (есть отложенный путь), жёсткая для обещания срока и для создания платёжной сессии в том же вызове |
| 11 | Оформление → Oracle, RETRY_DELIVERY_QUEUE | `order_id, retry_after = +10 минут` | Таблица как очередь, пакетная обработка | Мягкая, отложенная |
| 12 | Оплата → платёжный провайдер | `createSession(order_id, total, paymentType)` → `sessionId, redirectUrl` | Синхронный вызов | Жёсткая: при неуспехе оформление завершается исключением |
| 13 | Оформление → Oracle, ORDERS | `payment_session_id, delivery_partner` | Прямой SQL update после установки статуса | Жёсткая для дальнейшей оплаты и доставки |
| 14 | Пакетный контур → статусы, Oracle | Переходы статусов, повтор резерва, доступность маршрутов | Процедуры по расписанию, ночные SQL-скрипты | Скрытая: меняет состояние вне основного кода |
| 15 | Логистические интеграции ↔ службы доставки | Заявки, подтверждения | REST, брокер, пакетные выгрузки или промежуточный .NET-сервис, в зависимости от партнёра; семантика at-least-once или опрос таблицы | Жёсткая для доставки; подтверждения приходят с задержкой, повторы дают дубли |
| 16 | Логистические интеграции → склады | Не описано | Не описано | Не известно |
| 17 | Административные инструменты → статусы | Ручной перевод в технический статус | Ручная операция | Компенсирует зависшие заказы; вне формального цикла |
| 18 | Python-задания → Oracle | Прямые SQL, исторические выборки; также staging, API сервисов, CSV | Опрос, пакетно и почти в реальном времени | Мягкая для заказа, но создаёт нагрузку на операционную БД в пиковые окна |
| 19 | BI → Oracle | Отчётные запросы | Прямые запросы | Мягкая для заказа, нагрузка на БД |
| 20 | Уведомления → клиент | Письма о статусе | Частично асинхронно | Мягкая |

Oracle встречается в десяти строках из двадцати. Это главный кандидат на скрытую связность: изменение таблицы или пакета затрагивает сразу несколько взаимодействий, а реестра потребителей нет (Г-10).

## 3. Сценарий оформления заказа: шаги и последствия сбоев

Все шаги ниже выполняются в одном вызове оформления.

| Шаг | Действие | Зависимость | Что происходит при сбое или особом случае |
|---|---|---|---|
| 1 | Заказ создаётся со статусом `NEW` | — | — |
| 2 | Сумма считается по позициям; для канала `MARKETPLACE` добавляется сервисный сбор 49, для региона `FAR_EAST` надбавка 350 | Правила в коде | Изменение сбора или надбавки требует релиза монолита |
| 3 | Скидка считается промо-сервисом; если ответ пустой, вызывается PL/SQL-пакет в Oracle; флаг `disablePromos` отключает промо целиком | Промо-сервис, Oracle | Резервный расчёт получает только клиента, регион и промокод, без состава корзины. Исключение промо-сервиса на этом уровне не обрабатывается |
| 4 | Заказ сохраняется в ORDERS | Oracle | — |
| 5 | Строка экспорта пишется в INT_ORDER_EXPORT | Oracle, .NET-сервис | Экспорт происходит до выбора маршрута и оплаты, поэтому .NET-сервис видит и заказы, которые потом уйдут в ручную проверку или упадут на оплате |
| 6 | Выбирается правило маршрута; если правило требует ручной проверки, ставится `WAITING_MANUAL_REVIEW` и оформление завершается | Таблицы правил | Заказ остаётся без резерва доставки и без платёжной сессии (Г-18) |
| 7 | Слот резервируется у службы доставки | Служба доставки | При неуспехе ставится `DELIVERY_PENDING`, заказ попадает в RETRY_DELIVERY_QUEUE, клиент получает «принят с отложенной доставкой», платёжная сессия не создаётся. Таймаут или исключение вызова на этом уровне не обрабатываются |
| 8 | Создаётся платёжная сессия | Платёжный провайдер | При неуспехе ставится `PAYMENT_PENDING` и выбрасывается исключение; доставка уже зарезервирована, компенсации нет |
| 9 | Ставится `CONFIRMED`, затем отдельным запросом записываются `payment_session_id` и `delivery_partner` | Oracle | `CONFIRMED` означает «сессия оплаты создана», а не «заказ оплачен»; статус и атрибуты пишутся разными запросами |

Ключа идемпотентности на входе нет: повторный вызов создаёт новый заказ, новую строку экспорта и новый резерв доставки. Есть ли защита выше по цепочке вызова, не известно. Границы транзакции не видны (Г-17).

Состояние заказа в этом сценарии пишут три механизма: сохранение сущности, сервис статусов и прямой SQL. Три из пяти статусов сценария (`WAITING_MANUAL_REVIEW`, `DELIVERY_PENDING`, `PAYMENT_PENDING`) не входят в формальный жизненный цикл `new → confirmed → reserved → paid → shipped → delivered / cancelled`. Порядок тоже расходится: доставка резервируется до `CONFIRMED`, а в формальном цикле `reserved` идёт после `confirmed`.
