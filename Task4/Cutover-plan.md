# cutover-plan.md — план переключения ключевого перехода

> Назначение документа: описать конкретное включение изменения в рабочем контуре: цель переключения, условия запуска, роли, пошаговый сценарий, состояние данных, наблюдаемость, сравнение нового поведения со старым и rollback-сценарий.

Переход выбран потому, что это первое переключение пользовательского чтения на новый контур. Ошибка здесь сразу видна клиентам и поддержке, и именно здесь возникает риск потери прозрачности на переходе. Остальные ключевые переходы перечислены в разделе 10 `migration-roadmap.md`.

Числовые параметры окна (доля клиентов, длительность срабатывания алертов, время реакции) — предложение, которое утверждается на go/no-go. Пороги качества отсчитываются от базовой линии этапа 0 или от допустимой задержки состояния (Г-06).

## 1. Цель переключения

Цель переключения — перевести сценарий «посмотреть, что происходит с заказом» для пилотной группы операторов и пилотной доли клиентов с текущего поведения (разные интерфейсы читают статус из Oracle и витрины статусов, внутреннее состояние оператор собирает по нескольким системам) на новый контур: сервис состояния заказа, который строит клиентский статус, внутреннее состояние с шагом и причиной отклонения и историю изменений из журнала событий. После переключения система должна показывать клиенту понятный статус без ложных обещаний, а оператору показывать шаг, причину и историю на одном экране. Данные в сервисе состояния должны совпадать с Oracle для всех заказов, которые не менялись дольше окна задержки. Обращения «что с заказом» и время обработки обращения должны оставаться не выше базовой линии. Старый путь чтения сохраняется как резерв и источник сверки до завершения этапа 2 и выполнения условия его отключения.

## 2. Объём переключения

### 2.1. Включаем

- Экран состояния заказа в инструментах поддержки для пилотной группы: клиентский статус, внутреннее состояние с шагом и причиной, признак ручного сценария, история изменений срока, состава, способа доставки и статуса.
- Клиентский статус и история заказа в личном кабинете для пилотной доли клиентов.
- Показ времени последнего обновления состояния в обоих интерфейсах.

### 2.2. Не включаем

- Ручные действия поддержки: перевод в технический статус, флаги ручного разбора и повторной проверки остаются в админке монолита.
- Письма и уведомления клиентам: их по-прежнему формирует монолит.
- Статусы, которые RetailCore передаёт маркетплейсам, и заказы, которые клиент видит на площадке маркетплейса.
- Запись статусов, пакетные процедуры, оформление заказа, аналитику, логистические интеграции, .NET-сервис.
- Остальных операторов и клиентов: их переключают в следующих окнах по критериям раздела 9.

### 2.3. Критерии успешного переключения

| Критерий | Целевое значение | Где проверяем | Кто подтверждает |
|---|---:|---|---|
| Расхождения клиентского статуса и внутреннего состояния с Oracle у заказов, не менявшихся дольше окна задержки | 0 | Дашборд теневого сравнения | Владелец сервиса состояния |
| Задержка от изменения в Oracle до обновления состояния, p95 | Не выше Г-06 | Метрики захвата и сервиса состояния | Дежурный эксплуатации |

| Обращения «что с заказом» от пилотной доли клиентов | Не выше базовой линии | CRM поддержки | Руководитель поддержки (Ольга) |
| Время обработки обращения пилотной группой | Не выше базовой линии | CRM поддержки | Руководитель поддержки (Ольга) |

## 5. Состояние данных до переключения

Сервис состояния ничего не пишет в Oracle. Источником истины для всех изменений заказа остаётся монолит и Oracle; меняется только то, откуда читают поддержка и личный кабинет пилотной доли.

| Данные / сущность | Источник истины до переключения | Источник истины после переключения | Подготовка до cutover | Проверка консистентности | Что делаем при расхождении |
|---|---|---|---|---|---|
| Текущий статус заказа | Oracle (ORDERS, история статусов) | Oracle для записи; сервис состояния для чтения пилотными потребителями | Загрузка активных заказов; теневое сравнение на этапе 2a | Постоянное сравнение сервиса с Oracle вне окна задержки | Единичное расхождение разбирается; расхождение у решающих статусов — триггер отката (10.1) |
| Клиентский статус | Витрина статусов личного кабинета | Сервис состояния, перевод статусов монолита в клиентскую модель | Согласованная таблица перевода, включая `CONFIRMED` без обещания оплаты | Перевод, применённый к статусу из Oracle, совпадает со статусом в сервисе | Исправление перевода; до исправления откат личного кабинета |
| Внутреннее состояние с причиной | Нет: оператор собирает по админке, логам и соседним командам | Сервис состояния | Каталог причин согласован с поддержкой | Выборочная проверка пилотной группой по сценариям 8.3 | Неверная причина фиксируется, оператор работает по старому экрану до исправления |
| История изменений заказа | Технические таблицы, собирается вручную | Сервис состояния: события с начала работы журнала плюс история статусов, загруженная для активных заказов | Загрузка истории статусов активных заказов из Oracle | Сравнение истории статусов с таблицей истории Oracle | История до начала журнала помечается как возможно неполная |
| Специальные статусы маркетплейсов и логистического партнёра | Oracle | Сервис состояния через слой перевода | Перевод проверен на выборке | Выборка заказов маркетплейсов пилотной группой | Непереведённый статус показывается оператору как «статус партнёра без перевода», клиенту — последний переведённый статус |
| Результат ручного действия поддержки | Oracle, пишет админка монолита | Oracle; в сервисе появляется через журнал с задержкой | Инструкция: результат действия виден через время задержки | Первое ручное действие в окне проверяется пилотной группой | Если результат не появился за окно задержки — триггер 10.1 |
| Позиция чтения событий сервисом состояния | Не применимо | Брокер | Зафиксирована позиция на начало окна | Отставание потребителя в пределах окна задержки | Рост отставания — деградированный режим 10.4 |

## 8. Проверки после переключения

### 8.1. Технические проверки

| Проверка | Ожидаемое значение | Источник | Что делать при нарушении |
|---|---:|---|---|
| Доступность сервиса состояния | Не хуже старого чтения | Дашборд сервиса | Интерфейсы автоматически возвращаются на старое чтение; разбор |
| Ошибки чтения в поддержке и личном кабинете | Не выше старого чтения | Дашборд, логи | Откат по 10.1 |
| Задержка журнала и отставание потребителя | Не выше Г-06 | Дашборд журнала и брокера | Деградированный режим 10.4 |
| Нагрузка Oracle от захвата | В пределах порога эксплуатации | Мониторинг Oracle | Отключить захват, откат обоих переключателей |

### 8.2. Проверки данных

| Проверка | Ожидаемое значение | Метод сверки | Что делать при расхождении |
|---|---:|---|---|
| Число активных заказов | Совпадает в Oracle и в сервисе | Запрос к Oracle и к сервису | Догрузка пропущенных; при повторе — остановка |
| Состояния и статусы | Совпадают вне окна задержки | Теневое сравнение перевода статуса из Oracle и статуса в сервисе | Разбор; у решающих статусов — откат |
| Дубли и потери событий | Нет потерь; повторы отброшены по `event_id` | Сверка идентификаторов событий с историей статусов | Потеря — остановка расширения и разбор захвата |
| История заказа | Совпадает с историей статусов Oracle для периода работы журнала | Выборка заказов | Исправление; пометка неполной истории для периода до журнала |

### 8.3. Проверки поведения нового контура относительно старого

| Сценарий | Ожидаемое поведение нового контура | Как сравниваем со старым | Допустимое расхождение | Решение при отклонении |
|---|---|---|---:|---|
| Обычный заказ сайта, статус `CONFIRMED` | Клиенту не показывается «оплачен»: статус означает только созданную платёжную сессию; оператор видит шаг «платёжная сессия создана» | Shadow mode и ручная сверка с админкой | 0 вне окна задержки | Исправить перевод; откат личного кабинета |
| Заказ в ручной проверке, `WAITING_MANUAL_REVIEW` | Клиент видит понятный статус проверки; оператор видит причину: правило маршрута требует ручной проверки | Ручная сверка пилотной группой | 0 | Исправить причину; оператор работает по старому экрану |
| Отложенная доставка, `DELIVERY_PENDING` | Клиенту не показывается подтверждённый срок; оператор видит, что резерв доставки ожидает повтора | Ручная сверка и shadow mode | 0 | Откат личного кабинета |
| Ожидание оплаты после сбоя платёжной сессии, `PAYMENT_PENDING` | Клиент видит, что заказ ожидает оплаты; оператор видит причину | Ручная сверка | 0 | Исправить перевод |
| Частичная отмена | История показывает, что и когда отменено | Сравнение с историей статусов Oracle | 0 для периода работы журнала | Исправить; пометка неполной истории |
| Изменение срока доставки | История показывает прежний и новый срок | Сравнение с Oracle | 0 для периода работы журнала | Исправить |
| Заказ маркетплейса со специальным статусом | Оператор видит переведённое состояние | Выборка пилотной группой | 0 | Показ «статус партнёра без перевода» до исправления |
| Ручной перевод заказа в технический статус через админку | Новое состояние появляется в сервисе в пределах окна задержки | Первое такое действие в окне проверяется пилотной группой | Не дольше окна задержки | Деградированный режим или откат |

### 8.4. Операционные проверки

| Проверка | Кто проверяет | Ожидаемое состояние | Что делать при проблеме |
|---|---|---|---|
| Поддержка видит новый статус и причину | Пилотная группа | Оператор отвечает клиенту без обращения в соседние команды | Разбор с командой сервиса; при массовой проблеме — откат |
| Инструкции поддержки применимы | Руководитель поддержки (Ольга) | Операторы понимают, где делать ручные действия и когда их результат появится | Дополнить инструкцию |
| Статус в личном кабинете не противоречит письму | Пилотная группа по выборке | Формулировки согласованы | Откат личного кабинета до исправления текстов |

## 9. Критерии стабилизации после переключения

| Период наблюдения | Что должно быть стабильно | Порог | Решение |
|---|---|---:|---|
| Первые 15 минут | Ошибки чтения, расхождения, работа экрана у пилотной группы | Ошибок не больше старого чтения; расхождений вне окна задержки нет | Продолжить / откатить |
| Первый час | То же плюс задержка журнала и нагрузка Oracle; готовность к шагу личного кабинета | Метрики раздела 6 в норме | Продолжить с личным кабинетом / оставить только поддержку / откатить |
| Первый день | Обращения «что с заказом» пилотных клиентов, время обработки пилотной группы, жалобы на противоречие с письмами | Не выше базовой линии; подтверждённых жалоб нет | Переключить всю поддержку / оставить пилот / остановить |
| Первая неделя | Все критерии раздела 2.3, включая день с нагрузкой не ниже типичного пика | Все критерии выполнены | Планировать окна расширения личного кабинета / пересмотреть этап 2 |

## 10. Rollback-сценарий

### 10.1. Условия запуска rollback

| Триггер rollback | Порог | Кто принимает решение | Максимальное время реакции |
|---|---:|---|---|
| Расхождение решающих статусов (подтверждён, оплачен, отменён, доставлен) с Oracle вне окна задержки | Любое подтверждённое | Дежурный эксплуатации без согласования | 5 минут |
| Ошибки чтения в поддержке или личном кабинете | Выше старого пути чтения дольше 5 минут | Дежурный эксплуатации без согласования | 5 минут |
| Нагрузка Oracle от захвата изменений | Выше порога эксплуатации | Data / DBA без согласования | 5 минут |
| Задержка состояния выше Г-06 после перехода в деградированный режим | Дольше до конца активной фазы | Руководитель переключения | 15 минут |
| Подтверждённые жалобы клиентов на противоречие статуса и письма | Хотя бы одна системная (повторяется на однотипных заказах) | Руководитель переключения по данным поддержки | 15 минут |
| Пилотная группа не может ответить клиенту по новому экрану там, где могла по старому | Повторяется на однотипных заказах | Руководитель переключения | 15 минут |

### 10.2. Шаги rollback

| Шаг | Действие | Ответственный | Проверка результата | Что делать с данными, созданными в новом контуре |
|---:|---|---|---|---|
| 1 | Выключить переключатель личного кабинета: пилотные клиенты возвращаются на витрину статусов | Дежурный эксплуатации или команда сервиса | Запросы страницы заказа идут по старому пути | Бизнес-данных новый контур не создавал; производное состояние сохраняется для разбора |
| 2 | Выключить переключатель поддержки: пилотная группа возвращается на старый экран | Команда сервиса | Операторы видят старый экран | То же |
| 3 | Журнал событий и сервис состояния остаются в теневом режиме; захват отключается, только если триггером была нагрузка на Oracle | Data / DBA, дежурный эксплуатации | Теневое сравнение продолжается или захват остановлен | После повторного включения захвата — сверка с Oracle и догрузка с последней подтверждённой позиции, повторы отбрасываются по `event_id` |
| 4 | Выгрузить заказы с расхождениями, пилотных клиентов, открывавших страницу заказа в окне, и обращения пилотной группы | Архитектор, руководитель поддержки (Ольга) | Список передан поддержке и команде сервиса | Используется для проактивных ответов клиентам и разбора дефекта |
| 5 | Сообщить поддержке, бизнес-владельцу и команде разработки о причине и состоянии | Руководитель переключения | Сообщения отправлены по разделу 11 | — |

### 10.3. Состояние после rollback

| Область | Ожидаемое состояние после отката | Как проверяем |
|---|---|---|
| Трафик | Личный кабинет и поддержка читают старый путь | Мониторинг запросов обоих путей |
| Данные | Изменений в Oracle новый контур не делал; спорные заказы в списке шага 4 | Сверка списка с Oracle |
| Очереди / события | Журнал работает в теневом режиме или остановлен с зафиксированной позицией; неконтролируемой повторной обработки нет | Отставание потребителя, отчёт по повторам |
| Пользовательские статусы | Пилотные клиенты видят статус витрины, как до переключения; ложных обещаний нет | Выборка страниц заказов |
| Поддержка | Работает по прежней инструкции и знает, каким клиентам мог показываться новый статус | Подтверждение руководителя поддержки |

### 10.4. Деградированный режим

| Проблема | Временное решение | Допустимая длительность | Критерий выхода |
|---|---|---|---|
| Задержка состояния выше Г-06, но данные корректны | Показывать время последнего обновления и пометку «статус обновляется»; не расширять переключение | До конца активной фазы | Задержка вернулась в норму или откат по 10.1 |
| Сервис состояния недоступен | Интерфейсы автоматически читают старый путь | До восстановления сервиса | Сервис доступен, сравнение без расхождений |
| История заказа неполная для периода до запуска журнала | Пометка «история до даты запуска журнала может быть неполной» | Постоянно для таких заказов | Не требуется |
| Специальный статус партнёра без перевода | Оператору — «статус партнёра без перевода», клиенту — последний переведённый статус | До исправления перевода | Перевод добавлен и проверен |

## 11. Коммуникационный план

| Аудитория | Когда сообщаем | Что сообщаем | Канал | Ответственный |
|---|---|---|---|---|
| Команда разработки | До, во время, после | Окно, запрет других переключений, результат и дефекты | Канал окна переключения | Руководитель переключения |
| Эксплуатация | До, во время, после | Метрики, алерты, пороги отката, право выключить переключатель без согласования | Канал окна, дежурный телефон | Архитектор |
| Поддержка | До и после; во время для пилотной группы | Новый экран, где делать ручные действия, когда виден их результат, что говорить клиенту при откате | Канал поддержки, база знаний | Руководитель поддержки (Ольга) |
| Бизнес-владелец | До и после | Окно, допустимый риск, итог, предложение о расширении | Встреча, письмо | Руководитель переключения |
| Клиенты | Только при откате, если пилотный клиент обращается | Персональный ответ поддержки по списку шага 4 раздела 10.2; массовой рассылки нет | Каналы поддержки | Руководитель поддержки (Ольга) |

## 12. Итоговое решение после окна переключения

Раздел заполняется по итогам окна.

| Вопрос | Ответ |
|---|---|
| Переключение признано успешным? | Да, если выполнены все критерии раздела 2.3 за первый день; частично, если поддержка переключена, а личный кабинет откатан |
| Какие критерии выполнены? | Перечень из раздела 2.3 с фактическими значениями |
| Какие отклонения обнаружены? | Заказы с расхождениями, дефекты перевода статусов, жалобы |
| Какие действия нужны после cutover? | Исправления, дополнение инструкций, план окон расширения |
| Можно ли переходить к следующему этапу roadmap? | Этап 6 — только после стабилизации первой недели; расширение личного кабинета — отдельными окнами по этому же плану |

## 13. Проверка качества cutover-плана

- [x] указано, что именно переключается и в каком объёме;
- [x] есть go / no-go условия;
- [x] роли и ответственность не описаны общими словами, а привязаны к действиям;
- [x] сценарий переключения пошаговый и проверяемый;
- [x] состояние данных до, во время и после переключения описано отдельно;
- [x] есть наблюдаемость: метрики, дашборды, алерты, владельцы;
- [x] новый контур сравнивается со старым через конкретные сценарии и пороги;
- [x] rollback включает код, маршрутизацию, данные, очереди, статусы и коммуникацию;
- [x] есть критерии стабилизации после переключения;
- [x] по итогам cutover можно принять решение о продолжении roadmap.
